# 需求擷取

此內容於第三階段起始時載入 — 協作對話（第零至二階段）已產生值得保存之持久決策。

---

此文檔應如輕量 PRD 而無 PRD 儀式。納規劃所需之要，略無益之段落。

需求文檔用於產品定義與範圍控制。**勿**納實施細節如函式庫、schema、端點、檔案佈局或碼結構 — 除非腦力激盪本質為技術性且此等細節本身即為決策主題。

**非簡易工作之必含內容：**
- 問題框架
- 具體需求或預期行為附穩定 ID
- 範圍邊界
- 成功標準

** materially 有用時納入：**
- 關鍵決策及理據
- 依賴或假設
- 待決問題
- 已考量之替代方案
- 高階技術方向 — 僅當工作本質為技術性且方向為產品/架構決策之一部分

**文檔結構：** 用此模板，略去顯然不適用之可選段落：

```markdown
---
date: YYYY-MM-DD
topic: <kebab-case-topic>
---

# <Topic Title>

## Problem Frame
[受影響者、變更內容、何以重要]

## Requirements

**[群組標頭]**
- R1. [本群之具體需求]
- R2. [本群之具體需求]

**[群組標頭]**
- R3. [本群之具體需求]

## Success Criteria
- [何以知此解正確問題]

## Scope Boundaries
- [刻意排除之非目標]

## Key Decisions
- [決策]: [理據]

## Dependencies / Assumptions
- [僅於要緊時納入]

## Outstanding Questions

### Resolve Before Planning
- [影響 R1][用戶決策] [規劃前必答之問題]

### Deferred to Planning
- [影響 R2][技術] [規劃或碼庫探索時應答之問題]
- [影響 R2][需研究] [規劃時或需研究之問題]

## Next Steps
[若 `Resolve Before Planning` 為空: `-> /ce-plan` 作結構化實施規劃]
[若 `Resolve Before Planning` 非空: `-> 續 /ce-brainstorm` 以先決阻塞問題]
```

**視覺溝通** — 當需求有視覺輔助會顯著更易理解時納入。讀 `references/visual-communication.md` 了解決策標準、格式選擇及放置規則。

**標準**及**深度**腦力激盪通常應有需求文檔。

**輕量**腦力激盪保持文檔精簡。用戶僅需簡要對齊且無持久決策需保存時，可跳過文檔建立。

極小需求文檔僅 1-3 簡單需求時，純條列需求可接受。**標準**及**深度**需求文檔用穩定 ID 如 `R1`、`R2`、`R3`，俾規劃及後續審閱可明確引用。

需求跨多個不同關注點時，以粗體主題標頭分組。分組觸發條件為不同邏輯領域，非項目數量 — 即使四項需求跨三主題亦宜分組。按邏輯主題分組（如「打包」、「遷移與兼容」、「貢獻者工作流」），非按討論順序。需求保留原始穩定 ID — 編號不因分組重啟。需求歸最適之組；勿跨組重複。所有需求皆關同一事時方免分組。

工作簡易時合併段落而非填充。簡短需求文檔優於臃腫者。

定稿前檢查：
- 若此腦力激盪即止，`ce-plan` 尚需發明什麼？
- 有需求依賴聲稱超出範圍之物？
- 有未決項實為產品決策非規劃問題？
- 實施細節是否不當洩入？
- 有需求聲稱基礎設施不存在而未對碼庫驗證？若是，現驗證或標為未驗假設。
- 有低成本變更可使其 materially 更有用？
- 視覺輔助（流程圖、比較表、關係圖）是否比純文字更能助讀者快速理解需求？

若規劃仍需發明產品行為、範圍邊界或成功標準，腦力激盪尚未完成。

寫入前確保 `docs/brainstorms/` 目錄存在。

文檔含待決問題時：
- `Resolve Before Planning` 僅用於真正阻塞規劃之問題
- 若 `Resolve Before Planning` 非空，預設於腦力激盪中繼續處理此等問題
- 若用戶明示欲續行，將各餘項轉為明確決策、假設或 `Deferred to Planning` 問題後方續行
- 勿為消除不確定性而強制於腦力激盪中解決技術問題
- 技術問題或需驗證/研究之問題歸入 `Deferred to Planning`（該處更宜解答）
- 用 `[Needs research]` 等標記當規劃者應研究而非僅從倉庫上下文作答
- 顯式前推遞延問題，勿視為需求文檔未完成之失敗
